# 第28课时：Agentic RAG 技术原理与数据合成

RAG（检索增强生成）系统的效果高度依赖**训练数据质量**。传统 RAG 数据构建面临三大困境：**数据稀缺**（领域文档难以大规模标注）、**质量参差**（模板生成问题过于简单或噪声大）、**场景单一**（难以覆盖多跳检索、层级推理等复杂任务）。

> ✅ **Agentic RAG** 是一种**基于 LLM Agent 的自动化数据合成范式**，通过多阶段规划、检索、验证的 Agent 式流程，从原始文档自动生成高质量、可验证的 RAG 训练数据，并支持后续 RL 奖励构建与 Agentic RAG 模型训练。

本课以**技术原理为主线**，系统讲解 Agentic RAG 的核心思想、架构与主流模式，并在此基础上介绍 **Agentic RAG 数据合成**的方法论与 LazyLLM 实现。

---

## 1. 概述：RAG 的代际演变

在深入 Agentic RAG 之前，我们需要理解传统 RAG 的局限性，这构成了 Agentic RAG 诞生的历史背景。

### 1.1 线性 RAG（Naive RAG）
早期的 RAG 系统遵循“**查询 -> 检索 -> 生成**”的线性流程。
*   **特点**：结构简单，易于部署。
*   **痛点**：
    *   **检索僵化**：一旦检索到的上下文不相关，LLM 只能基于错误的上下文“一本正经地胡说八道”或直接回答不知道。
    *   **缺乏反思**：系统无法判断检索结果的质量，也无法自我修正。

### 1.2 高级 RAG（Advanced RAG）
引入了查询重写、混合检索、重排序等技术，提升了检索质量。但本质上仍是**静态流程**，无法根据问题的复杂度动态调整策略。

### 1.3 模块化 RAG（Modular RAG）
开始引入路由和模块化组件，允许根据问题类型选择不同的检索路径。这为 Agentic RAG 奠定了基础。

### 1.4 Agentic RAG（代理式 RAG）
这是 RAG 的当前终极形态。其核心在于引入了 **Agent（智能体）** 的自主决策能力。
*   **定义**：Agentic RAG 不再是被动的检索工具，而是一个具备**规划、反思、工具使用**能力的智能系统。它能够判断“何时检索”、“检索什么”、“检索结果是否满意”以及“是否需要使用搜索引擎或其他工具”。

## 2. 内在原理：为什么需要 Agent？

Agentic RAG 的核心在于将 LLM 从“文本生成器”升级为“推理控制器”。其内在原理基于以下三个支柱：

### 2.1 认知架构
传统 RAG 类似于人类的“开卷考试”，考生只能翻书。而 Agentic RAG 类似于“研究员”，具备以下认知循环（即 ReAct 模式）：
1.  **推理**：分析用户问题，判断需要哪些信息源。
2.  **行动**：调用检索工具、数据库查询或网络搜索。
3.  **观察**：审视检索到的内容，评估相关性。
4.  **反思**：如果内容不足，调整搜索关键词或更换数据源，重新开始循环。

### 2.2 动态规划与纠错
在复杂场景下，单一检索往往无法解决问题。
*   **场景示例**：用户问“对比 A 公司和 B 公司去年的财报差异”。
*   **传统 RAG**：可能检索不到直接对比的文档，导致回答失败。
*   **Agentic RAG**：
    1. 规划：拆解为“查询 A 公司财报”和“查询 B 公司财报”两个子任务。
    2. 执行：分别检索。
    3. 整合：综合两个结果生成对比分析。
    4. 纠错：如果 B 公司财报缺失，Agent 可能会尝试使用 Web Search 工具补充。

### 2.3 工具使用
Agentic RAG 将检索视为众多工具中的一种。Agent 可以根据需要，在向量数据库、SQL 数据库、知识图谱、网络搜索引擎之间自由切换。

## 3. 核心架构与组件

一个标准的 Agentic RAG 系统通常包含以下核心组件：

### 3.1 Agent 大脑
这是系统的核心，通常由高性能 LLM（如 GPT-4, Claude 3, Llama 3）担任。其职责是：
*   **意图识别**：理解用户的真实需求。
*   **任务拆解**：将复杂问题分解为子任务。
*   **决策控制**：决定下一步是检索、计算还是直接回答。

### 3.2 工具集
Agent 手中的武器库，主要包括：
*   **向量检索器**：用于非结构化文本检索（RAG 核心）。
*   **结构化查询工具**：SQL 生成器、图数据库查询接口。
*   **网络搜索工具**：如 Tavily, Serper，用于获取实时信息。
*   **专用 API**：如计算器、代码解释器、天气 API 等。

### 3.3 记忆模块
*   **短期记忆**：当前对话的上下文，用于多轮对话中的指代消解。
*   **长期记忆**：将历史交互存入向量库，供 Agent 参考“过去的经验”。

### 3.4 规划器与评估器
*   **规划器**：生成执行路径。
*   **评估器**：在检索结果返回后，评估其与 Query 的相关性分数，决定是否需要二次检索。

## 4. 主流技术模式详解

在工程实践中，Agentic RAG 主要有以下几种主流实现模式：

### 4.1 路由模式
这是最简单的 Agent 形态。Agent 充当“分流器”，根据问题的类型将其引导至不同的数据源。
*   **逻辑**：
    *   如果是“事实性问题” -> 走向量检索。
    *   如果是“实时新闻” -> 走网络搜索。
    *   如果是“数值统计” -> 走 SQL 数据库。
*   **优势**：响应速度快，成本较低。

### 4.2 多文档代理
针对大规模知识库，将文档分组，每个组分配一个子 Agent。
*   **架构**：
    *   **顶层 Agent**：负责汇总各个子 Agent 的答案。
    *   **子 Agent**：只负责检索特定的文档切片库，并进行初步总结。
*   **适用场景**：法律文档审查、多领域知识库问答。
*   **优势**：避免了海量检索带来的噪声干扰，各司其职。

### 4.3 自我修正 RAG (Corrective RAG, CRAG)
这是目前最热门的架构之一，引入了“自我反思”机制。
*   **流程**：
    1.  **检索**：从向量库获取文档。
    2.  **评估**：使用 LLM 判断检索文档的相关性。
        *   如果**正确**：直接生成答案。
        *   如果**模棱两可**：进行“知识精炼”（如切片重排序）。
        *   如果**不相关**：丢弃文档，改用网络搜索或重写查询。
*   **核心价值**：极大缓解了检索噪声导致的幻觉问题。

### 4.4 自适应 RAG (Adaptive RAG)
利用强化学习或分类器，让系统自主决定处理策略。
*   **决策树**：系统预先判断问题的“复杂度”。
    *   简单问题 -> 直接由 LLM 回答（利用模型内部知识）。
    *   中等问题 -> 单次检索生成。
    *   复杂问题 -> 多步检索。
*   **核心价值**：在成本与质量之间寻找最优解。

## 5. 主流框架与工具生态

构建 Agentic RAG 离不开强大的框架支持。

### 5.1 LazyLLM

**LazyLLM** 在 RAG 领域提供**从数据合成到推理部署的一站式能力**，是构建 Agentic RAG 的优选框架。

*   **推理与检索链路**：
    *   **Document**：支持多种分块策略（CoarseChunk、FineChunk 等），与 Embedding、BM25 等无缝集成；
    *   **Retriever**：支持向量检索、BM25、混合检索，可灵活配置 topk 与相似度策略；
    *   **Reranker**：内置 BGE-Reranker 等重排序模型，支持在线/离线调用，实现“召回 + 精排”两阶段流程。
*   **Agentic RAG 数据合成**（核心差异化能力）：
    *   提供 **Atomic、Depth、Width** 三种 QA 形态的完整合成 Pipeline；
    *   算子化设计，支持 `atomic_rag_pipeline`、`depth_qa_pipeline`、`width_qa_pipeline` 开箱即用；
    *   内置 LLM 无文档验证、金标答案生成、QA F1 评估，可直接用于 RL 奖励构建；
    *   与 Document、Retriever、Reranker 等组件统一生态，形成“数据 → 训练 → 部署”闭环。
*   **适用场景**：领域知识库构建、RAG 数据自动生成、Embedding/Reranker 微调、Agentic RAG 训练数据准备。

### 5.2 LangChain & LangGraph
*   **LangChain**：提供了基础的链式结构和工具调用接口。
*   **LangGraph**：基于状态机图的概念，允许开发者精细定义 Agent 的循环、分支和条件判断逻辑。非常适合实现 CRAG 和多步推理流程。

### 5.3 LlamaIndex
LlamaIndex 在数据索引方面具有天然优势，其 `AgentRunner` 和 `ReActAgent` 组件封装度高。
*   **特点**：拥有强大的 `RouterQueryEngine` 和 `SubQuestionQueryEngine`，非常适合构建多文档代理架构。

### 5.4 AutoGen & CrewAI
这两个框架更侧重于多 Agent 协作。
*   **场景**：如果你需要一个“检索 Agent”和一个“写作 Agent”协作完成一篇综述，可以使用这些框架。它们更擅长角色扮演和群体智能。

## 6. Agentic RAG 数据合成

前述章节聚焦于 Agentic RAG 的**推理与检索**能力。然而，训练这类系统需要大量**高质量、可验证的 QA 数据**——这正是 **Agentic RAG 数据合成**要解决的问题：从原始文档自动生成适合 RAG/Agentic RAG 训练的数据，并支持 RL 奖励构建。

### 6.1 核心挑战：IR 问题与可召回问题

**IR（Information Retrieval）问题**是指**必须依赖检索文档才能正确回答**的问题，天然适合作为 RAG 训练数据。与之相对的是**可召回问题**：LLM 仅凭预训练知识即可回答，无需检索。若将可召回问题混入训练集，模型难以学到“何时检索”的边界。

| 问题类型 | 示例 | 是否需要检索 | 对 RAG 训练的价值 |
|----------|------|---------------|-------------------|
| **IR 问题** | “龙美术馆 2025 年 4 月展览时间范围？” | 是 | ✅ 高价值 |
| **可召回问题** | “什么是机器学习？” | 否 | ❌ 低价值（甚至有害） |

数据合成的首要目标：自动生成**仅能通过检索回答**的 QA 对，并**过滤**可召回问题。

### 6.2 三种数据形态：Atomic、Depth、Width

真实检索需求是**多层次的**，数据合成需覆盖三种形态：

| 形态 | 含义 | 生成思路 |
|------|------|----------|
| **Atomic（原子级）** | 单文档、单事实，一问一答 | 从文档提取原子结论 → 生成问题 → 验证 |
| **Depth（深度）** | 需多步检索、层级推理 | 从已有问题反向找父级主题 → 生成需先检索父级再定位子级的问题 |
| **Width（宽度）** | 多子问题合并的综合问题 | 合并相邻 QA 对 → 验证可分解性 → 过滤 |

### 6.3 Atomic QA 合成流程

1. **提取 identifier**：从文档中识别内容主题（实体、专有名词等）；
2. **提取结论**：将文档拆解为原子事实（不可再分、含明确标识如数值、时间）；
3. **生成问题**：根据 identifier、结论、关系 R 生成对应问题；
4. **清洗答案**：提取精确信息，标准化格式；
5. **LLM 无文档验证**：用 LLM 在无文档条件下回答，若答对则剔除（可召回问题）；
6. **金标答案**：基于文档生成标准答案，用于评估与 RL 奖励；
7. **可选答案**：生成答案变体，增强训练鲁棒性。

### 6.4 Depth QA 合成流程

从已有问题出发，**反向扩展**父级主题：

1. **Backward**：从子级 identifier 发散搜索父级 identifier 与关系；
2. **Superset 验证**：确保父级 + 关系能唯一定位子级；
3. **生成深度问题**：基于父级、关系、子级生成需多步检索的问题；
4. **可召回过滤**：同样用 LLM 无文档回答，过滤可召回样本。

支持**多轮迭代**：每轮以上一轮的父级作为新子级，继续扩展，生成更深层级问题。

### 6.5 Width QA 合成流程

将**相邻 QA 对**合并为综合问题：

1. **合并**：用 LLM 将 2–3 个相关子问题合成为综合问题；
2. **可分解性检查**：验证综合问题能否正确分解回原子问题；
3. **一致性过滤**：用 LLM 回答综合问题，与 golden 答案比较，过滤不一致样本。

### 6.6 质量保障与评估

| 机制 | 作用 |
|------|------|
| **LLM 无文档验证** | 过滤可召回问题，保证训练数据为“真 IR 问题” |
| **金标文档答案** | 基于原文生成标准答案，用于 F1 评估与 RL 奖励 |
| **QA F1 评分** | 比较预测与金标答案的 token 重叠度，筛选高质量样本 |

### 6.7 LazyLLM 的数据合成实现

LazyLLM 将上述流程封装为可组合的**算子 + Pipeline**，支持从原始文档到高质量 RAG 训练数据的端到端合成：

```python
from lazyllm.tools.data.pipelines.rag_pipelines import atomic_rag_pipeline, qa_evaluation_pipeline

llm = lazyllm.OnlineChatModule(source="openai", model="gpt-4o-mini")
ppl = atomic_rag_pipeline(llm=llm, input_key='text', max_per_task=10, max_question=10)
result = ppl([{'text': '龙美术馆 2025 年 4 月 28 日至 6 月 15 日举办「当代艺术展」...'}])

# QA F1 评估
eval_ppl = qa_evaluation_pipeline(prediction_key='re_answer', ground_truth_key='golden_answer', output_key='F1Score')
scored = eval_ppl([{'re_answer': item['refined_answer'], 'golden_answer': item['golden_doc_answer']} for item in result])
```

`depth_qa_pipeline` 与 `width_qa_pipeline` 分别支持深度与宽度问题的合成，可与 Atomic 输出串联使用。

## 7. 挑战与未来展望

### 7.1 当前挑战
1.  **延迟**：Agent 需要多次推理和多次检索，端到端响应时间显著增加，影响用户体验。
2.  **成本**：每次规划和反思都需要消耗 LLM Token，尤其是 GPT-4 级别模型的调用成本较高。
3.  **稳定性**：Agent 的推理过程具有不确定性，可能出现陷入死循环或错误规划的情况。

### 7.2 未来趋势
1.  **小模型驱动**：将路由和初步筛选功能下沉至更小、更快的模型（如 Llama 3 8B），降低延迟和成本。
2.  **流式输出与可视化**：在 Agent 思考和检索过程中，实时向用户展示进度条或思维链，缓解等待焦虑。
3.  **流图范式普及**：像 LangGraph 这样的图结构编排将成为标准，取代简单的线性 Chain。

---

## 总结

**Agentic RAG 标志着知识问答系统从“被动检索”向“主动思考”的质变。**

它不再仅仅依赖于向量相似度的匹配，而是通过 LLM 的推理能力，动态地选择工具、修正路径、评估结果。在**数据侧**，Agentic RAG 数据合成通过 Atomic、Depth、Width 三种形态的自动化生成，解决了 RAG 训练数据稀缺与质量参差的问题，并支持 RL 奖励构建。

虽然目前仍面临延迟和成本的挑战，但随着模型推理速度的提升和编排框架的成熟，Agentic RAG 将成为企业级知识库应用的标准范式。

对于开发者而言，掌握 LangGraph 或 LlamaIndex 中的 Agent 编排逻辑，理解 CRAG 和 ReAct 的设计模式，并善用 LazyLLM 等框架的**数据合成 Pipeline**，是构建下一代智能应用的关键。
