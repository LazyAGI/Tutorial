# 第6课时：基于 LazyLLM 的数据-训练-推理全流程实践

预训练（PT）里常说「数据决定上限」：同样一套训练与评测脚手架，换一套数据形态，模型学到的能力分布会差别很大。本课时把焦点放在**数据从哪里来、怎么被 pipeline 加工成训练格式**，再用同一套 LazyLLM 流程把「合成数据 → 训练 → 部署推理 → 指标对比」串成一条可复现链路，避免只见.loss 曲线却说不清数据里发生了什么。

我们会对照两条典型路线：一条走**纯文本续写**，让模型在连续语料上建模语言分布；另一条在清洗后的语料上**合成 Phi-4 风格的问答对**，把「长 context + 问答」显式写进训练目标。两条路线共享相近的基座、训练入口和评测指标，便于公平比较「数据形态」带来的差异，而不是被实现细节干扰。

对应到可运行工程，本课时整理两个真实实验脚本如下（详细逻辑见后文分节，此处只作路线图）：

- [`run_wikitext.py`](./code/run_wikitext.py)：纯文本预训练数据合成 pipeline
- [`run_phi4_wikitext.py`](./code/run_phi4_wikitext.py)：Phi-4 风格 Q&A 数据合成 pipeline

两者在训练与评测框架上基本一致，核心差异在于**数据流 pipeline**。下文按「数据流重点展开 + 训练部署通用讲解」组织，先吃透数据怎么流，再回头看训练与推理只是同一套管道上的不同阀门。

## 1. 任务总览

两个实验回答的是同一个**工程问题**：给定一款已经过 Instruction 对齐的中英小模型，还能否用「继续预训练（Continue PT）」在**自有数据分布**上再推一把？如果只是口头说「可以」，意义不大；本课把结论建立在三件可复现的事情上：**数据怎么造、训练怎么配、评测怎么评**。并且刻意让两条实验共用**同一基座、同一训练入口、同一套评测协议**，这样当你看到指标差异时，归因路径会清晰得多：**主要就是数据流不同**。

更具体地说：两个实验都在基座 `Qwen2.5-0.5B-Instruct` 上，使用 LLaMA-Factory 的 `stage='pt'` 做**全参数**继续预训练，并在同一评测脚本中对比「基座 vs PT 后」。真正不同的是「每个训练 step 里，模型眼睛看到的 `text` 长什么样」：

- **实验 A（纯文本）**：目标范式是 **prefix → continuation** 的自然续写。训练样本是连续维基 chunk（见第 2、3 节）；评测时把同分布文本切成「已给出的前缀」和「要让模型接上的后缀」，并**只在后缀上**统计 loss / PPL，再用生成结果算 BLEU。直觉：你在衡量模型有没有变得更像**百科式长文**。
- **实验 B（Phi-4 Q&A）**：目标范式是把 chunk **改写**成「Question: …\\nAnswer: …」的串，再当成一整段 `text` 做下一词预测。它并不是另起一套 RLHF，而是让 token 转移统计里**多出大量「问答接话」模式**。这类数据若由大模型离线合成，会带来额外成本与错误率，这也是pipeline-B与pipeline-A的重要差别。评测侧为了复用同一套函数，同样把样本整理成 `prefix`（问题侧）与 `continuation`（答案侧）。直觉：你在衡量模型有没有变得更像**简答题作答**。

一个常见的初学者疑问是：「实验 B 看起来像 SFT，为什么还叫 PT？」在这里的界定很简单：训练阶段仍然是对**整段** `text` 做自回归最大似然，没有单独的「只训 answer」或对话模板损失头；**任务形状的差别全部来自数据排版**。若你日后要追求「只优化答案区间」「对齐特定模板」，通常会在 PT 之后再接一轮 SFT——那是另一条独立流程，本课先把「数据形态 → PT → 指标」这一环讲透。

共同评测指标及**阅读时的直觉抓手**如下（公式与实现见第 5 节）：

- **PPL（困惑度）**：在 continuation token 上度量模型有多「惊讶」。同一次实验内，PPL 与平均 loss 通过指数关系联动，适合纵向对比「PT 前 vs 后」。
- **Loss（交叉熵）**：平均到 continuation 上每个 token 的负对数似然，数值越小表示拟合得越好；比 PPL 更线性、更利于看微调曲线。
- **BLEU（此处为轻量 2-gram F1 风格近似）**：度量生成文本与参考答案在局部片段上的重合度；**不是**人类主观分，但能快速暴露「模型是不是在瞎编词形」或「输出离参考太远」。

读完本节，可以带着一句话进第 2 节：**实验 A 把分布往「文章续写」推；实验 B 把分布往「问答接话」推；评测接口刻意统一，避免「换评测换结论」。**

## 2. 数据与产物

在打开任何脚本前，建议先建立对 `data/` 目录的心理模型：本课里绝大多数 `json/jsonl` 都是**自动生成物**，等价于「除了权重 checkpoint 以外的另一种可复现状态」。你可以删掉再跑 `--mode prepare` 再生，代价只是时间和算力；**但不要手改中间文件却又期待结果可复现**。另外务必记住依赖顺序：**实验 B 读取的是实验 A 清洗后的 `wikitext_cleaned.jsonl`**，若你跳过实验 A 直接跑 B，应先确认该文件已经存在且内容合理。

下面两小节分别对应两条实验的「源数据 → 中间态 → 训练/评测落地文件」。阅读时你可以自问三个问题：**这一行文本最终会不会进 `train.json`？评测时的 `prefix` 对应人类任务的哪一半？如果我把某一步过滤关掉，损失的是多样性还是质量？**

### 2.1 实验 A：WikiText-2 纯文本

WikiText-2 是经典的小型英文维基语料子集，句子级噪声少、领域混杂适中，很适合做**教学用继续预训练**：你不会一上来就被万亿 token 的数据工程淹没，但依然能观察到「清洗 + 分块」对可用 chunk 数量的影响。

- 来源：`wikitext/wikitext-2-raw-v1`，`train` split
- 原始非空行上限：`RAW_LOAD_SAMPLES=10000`
- pipeline 输出：约 `3966` 个 chunk（以实际运行为准）
- 训练集：`3000` 条，`data/wikitext_train.json`
- 评测集：`200` 条，`data/wikitext_eval.jsonl`

`RAW_LOAD_SAMPLES` 与最终 chunk 数不必相等：原始行经过长度门槛、语言检测与 token 切块后，** surviving 的 chunk 数量**才是真实可用于训练的上限。若你在复现时看到 chunk 明显变少，优先检查是否触发了过短/过长过滤，而不是怀疑「数据集本身变小了」。

原始样本示例：

```json
{
  "text": "Homarus gammarus , known as the European lobster ..."
}
```

### 2.2 实验 B：Phi-4 Q&A 合成

这一支线的直觉是：与其让模型只在「纯续写」上变强，不如在**同一段百科知识**上显式制造「问—答」对齐信号，让模型熟悉「问题触发什么 token 模式、答案通常多短、如何收尾」等统计规律。代价也很现实：**合成质量强依赖上游 LLM**——幻觉问答、文不对题的 query、把数字抄坏的 answer 都会进训练集，因此脚本里一般会过滤空 `qa_pairs`，你仍应在抽样的 jsonl 上人工 spot-check 几条。

- 来源：`data/wikitext_cleaned.jsonl`（由实验 A 清洗得到）
- 输入上限：`SOURCE_LOAD_LIMIT=2000`
- 每条 context 生成：`NUM_QA=3` 组 Q&A
- 中间文件：`data/phi4_wikitext_qa.jsonl`（仅保留 `qa_pairs` 非空记录）
- 训练集：`3000` 对，`data/phi4_train.json`
- 评测集：`200` 对，`data/phi4_eval.jsonl`

`NUM_QA=3` 表示尽量从每个 context 里榨出多条监督，但**不是**越多越好：问法过于雷同会让训练集「看起来很肥、信息很瘦」；若你抬高条数，建议同步观察合成耗时、API/显存成本，以及评测集 BLEU 是否出现异常波动。

合成后样本示例：

```json
{
  "context": "The beings in ancient Egyptian tradition ...",
  "qa_pairs": [
    {
      "query": "What is the estimated number of deities named in Egyptian texts?",
      "answer": "More than 1,400 deities are named in Egyptian texts."
    }
  ]
}
```

### 2.3 数据文件说明

本课时 `data/` 下面这些文件，建议你在脑中分成三类，就不容易迷路：

1. **原料与粗加工**：`wikitext_cleaned.jsonl`（清洗+切块后的 chunk，带 `uid` / `meta_data` 便于溯源）。
2. **任务专用半成品**：`phi4_wikitext_qa.jsonl`（已经挂上 `qa_pairs`，但仍保留 `context`，方便你抽查 LLM 是否跑题）。
3. **训练/评测直呼名**：`*_train.json` 与 `*_eval.jsonl`（进入 LLaMA-Factory 与评测循环的最终形态）。

它们全部是运行脚本后的生成物；手工编辑不是不可以，但一旦你这样做了，请在实验记录里写下改动点，否则「对比实验」会失去意义。

- 实验 A（`run_wikitext.py`）会生成：
  - `data/wikitext_cleaned.jsonl`
  - `data/wikitext_train.json`
  - `data/wikitext_eval.jsonl`
- 实验 B（`run_phi4_wikitext.py`）会生成：
  - `data/phi4_wikitext_qa.jsonl`
  - `data/phi4_train.json`
  - `data/phi4_eval.jsonl`

建议先执行 `--mode prepare` 生成数据，再执行 `--mode train` 或 `--mode full`。如果本地不存在这些文件，属于正常情况，需要先跑对应脚本。若你希望节省重复的 LLM 调用时间，请在第一次做完 `prepare` 后**妥善备份** `*_cleaned.jsonl` 与 `*_qa.jsonl`，下次改训练超参时可以直接复用。

## 3. 数据流 (Data Flow) 管理

从这里开始，两条实验开始「分道扬镳」，但你可以用**同一张追问清单**来理解每一步：`输入字段是什么？` → `pipeline 调了 LazyLLM 里哪个 build_*？` → `输出字段多了什么？` → `写盘时为了训练/评测又做了什么 reshape？`

读懂第 3 节后，再回头看第 4 节的 `cutoff_len` 与 batch 设置，你会自然理解它们其实是在约束「**每一步塞进 GPU 的 token 预算**」，而预算必须与第 3 节产出的文本长度分布相匹配。

本节是两个实验的关键差异。

### 3.1 Pipeline-A：`build_text_pt_pipeline`（纯文本清洗分块）

目标：把原始文章转换为高质量预训练 chunk。

这一 pipeline 解决的是**脏数据到可用 token 预算内连续文本**的转化：WikiText 原始行里既有正常段落，也有过短行或排版噪声；若不清洗直接 PT，容易浪费训练步、稀释有效梯度。`build_text_pt_pipeline` 可理解为**质量过滤 + 近似按 token 长度切块**：让每条 `content` 大致落在 `min_tokens`～`max_tokens` 区间内，并对语言等字段做约束（本课为英文）。你在调参时若改 `max_tokens`，要同时想到两件事——**单条样本变长会吃显存**，以及**chunk 变长会改变「前后文依赖」的统计**，评测侧也要留意 `prefix_len` 与截断上限是否还够用。

处理逻辑（建议与 `run_wikitext.py` 对照着读）：

1. 读取 WikiText 非空行（最多 10000 条）。
2. 调用 `build_text_pt_pipeline(...)` 做长度过滤、语言检测、token 级切块。
3. 输出 chunk 列表（核心字段 `content`）。
4. 训练集：`content -> text` 写入 JSON。
5. 评测集：对 `content` 按句子边界切分为 `prefix/continuation` 写入 JSONL。

数据形态（处理前 vs 处理后）：

- 处理前（原始输入，来自 HuggingFace `wikitext-2-raw-v1`）：

```json
{
  "text": "Homarus gammarus , known as the European lobster ..."
}
```

- 处理后中间产物（`data/wikitext_cleaned.jsonl`，单行）：

```json
{
  "uid": "20260316143650_55db881fd2bb4b4baa85f2626860f9d1",
  "content": "This ammunition , and that which I brought with me ...",
  "meta_data": {
    "index": 0,
    "total": 1,
    "length": 926
  }
}
```

- 训练样本（`data/wikitext_train.json`）：

```json
{
  "text": "Through contact with neighboring civilizations , the Egyptians also adopted foreign deities ..."
}
```

- 评测样本（`data/wikitext_eval.jsonl`，单行）：

```json
{
  "prefix": "Through contact with neighboring civilizations ...",
  "continuation": "In Greek and Roman times, from 332 BC to the early centuries AD ..."
}
```

关键代码（节选）：

```python
dataset = load_dataset('wikitext', 'wikitext-2-raw-v1', split='train')
raw_texts = [row['text'].strip() for row in dataset if row['text'].strip()][:RAW_LOAD_SAMPLES]

ppl = build_text_pt_pipeline(
    content_key='content',
    language='en',
    min_chars=100,
    max_chars=100000,
    max_tokens=1024,
    min_tokens=100,
)
chunks = ppl([{'content': t} for t in raw_texts])
```

该 pipeline 的输出仍是“连续文本块”，适合做标准语言模型续写预训练。

训练与评测的形态差异值得再强调一次：`wikitext_train.json` 里是一条完整 chunk，模型在训练时会对**整段**文本做下一词预测；而 `wikitext_eval.jsonl` 刻意拆成 `prefix/continuation`，是为了让 `compute_ppl` 能把损失**只压在续写段**上，这与「人类评测续写质量」的设定一致。若跳过这一步、直接对全文算 loss，前缀里极易预测的 token 会把平均 loss「拉好看」，却不代表续写真的变好。

### 3.2 Pipeline-B：`build_phi4_pt_pipeline`（Q&A 合成）

目标：把文本 chunk 转换为 Phi-4 风格问答对，强化“问题到答案”的生成模式。

这一 pipeline 的本质是**用外部 LLM 把无标签正文压缩成有监督形态的伪标签**。好处是训练目标更「任务化」，模型更容易学到短答、指称一致等模式；坏处是所有错误都会被烙进梯度——因此 `valid = [rec for rec in results if rec.get('qa_pairs')]` 只是最低限度的空值过滤，**不能代替人工或规则抽检**。如果你在 `qa_pairs` 里看到明显离题，优先检查上游 `context` 是否过短、合成 prompt 是否过宽、或解码温度是否过高。

处理逻辑：

1. 从 `wikitext_cleaned.jsonl` 读取 `content`。
2. 调用 `build_phi4_pt_pipeline(context_key='context', llm=llm, num_qa=3)`。
3. 每条记录新增 `qa_pairs`。
4. 过滤：仅保留 `qa_pairs` 非空记录。
5. 展开为 `(query, answer)` 列表后，分别构造训练/评测数据。

数据形态（处理前 vs 处理后）：

- 处理前（输入 context，来自 `data/wikitext_cleaned.jsonl`）：

```json
{
  "uid": "20260316143652_87ffac79a045483dad3c81f27e71d4d9",
  "content": "The beings in ancient Egyptian tradition who might be labeled as deities are difficult to count ...",
  "meta_data": {
    "index": 0,
    "total": 1,
    "length": 440
  }
}
```

- 处理后中间产物（`data/phi4_wikitext_qa.jsonl`，单行）：

```json
{
  "context": "The beings in ancient Egyptian tradition ...",
  "qa_pairs": [
    {
      "query": "What is the estimated number of deities named in Egyptian texts?",
      "answer": "More than 1 @,@ 400 deities are named in Egyptian texts."
    }
  ]
}
```

- 训练样本（`data/phi4_train.json`）：

```json
{
  "text": "Question: Who was the artist that influenced Barker the most?\nAnswer: John Everett Millais and Edward Burne-Jones"
}
```

- 评测样本（`data/phi4_eval.jsonl`，单行）：

```json
{
  "prefix": "Who was the artist that influenced Barker the most?",
  "continuation": "John Everett Millais and Edward Burne-Jones"
}
```

关键代码（节选）：

```python
ppl = build_phi4_pt_pipeline(
    context_key='context',
    image_key=None,
    llm=llm,
    num_qa=NUM_QA,
)
results = ppl([{'context': ctx} for ctx in contexts])
valid = [rec for rec in results if rec.get('qa_pairs')]
```

展开为训练样本时，脚本把每条 QA 变成一整行 `text`（`Question: …` + `Answer: …`），这是在告诉模型：**在见到 Question 这一前缀后，Answer 的 token 序列应当如何继续**。评测阶段再把「到 Answer 为止」作为前缀、「答案正文」作为 continuation，于是第 5 节的 PPL/BLEU 仍然可比。若你未来想更贴近真实使用场景，可以考虑只把 Answer 标成 loss 区间（类似 SFT 里的 `labels mask` 思路），那就已经越过本课的 PT 设定，需要改训练代码而非只改数据。

简要说明：该 pipeline 不是“切块”，而是“生成式合成”，把无监督文本转为半结构化 QA 监督信号。

### 3.3 两种数据流对比

| 维度 | 纯文本 Pipeline | Phi-4 Pipeline |
|---|---|---|
| 输入 | 原始 WikiText 行文本 | 清洗后的 chunk |
| 核心算子 | `build_text_pt_pipeline` | `build_phi4_pt_pipeline` |
| 主要动作 | 过滤 + 切块 | LLM 生成 QA |
| 中间结果 | `content` chunk | `qa_pairs` |
| 训练样本形态 | `{"text": chunk}` | `{"text": "Question: ...\\nAnswer: ..."}` |
| 评测样本形态 | `prefix/continuation` | `query/answer` |

结论：两种数据流分别对应“文本建模能力”和“问答对齐能力”的增强路径，训练框架可复用，但数据构造目标不同。

当你在设计自己的业务 pipeline 时，可以借用本表做决策：**若你的线上流量主要是长文档续写、摘要素材、代码补全，偏向 pipeline-A 这一路；若流量以 FAQ、知识问答、客服为主，pipeline-B 更值得一试**，但要准备好合成质检与成本预算。

## 4. 通用训练教程

两个脚本都采用 LLaMA-Factory PT 全参数微调，核心参数基本一致。

为什么要用 `stage='pt'` 且 `finetuning_type='full'`？在本课的设定里，「继续预训练」希望**整体更新词嵌入与每一层 Transformer 的权重**，让表示空间跟随新语料分布漂移；这和 LoRA 等「只训适配器」的增量更新不是同一类问题——后者更适合在**冻结主体**的前提下做任务对齐，而前者更激进、也更吃显存。若你硬件吃紧，可以把本节当作「**理念参考**」，把 `full` 换成参数高效方案，但要接受：**可比性需要重新建立**，不宜与文中的全参结果直接并排硬比。

另一个容易忽略的细节是 `cutoff_len=512` 与第 3 节 chunk 长度的关系：训练时超过该长度的样本会被截断，意味着**长距离依赖超过 512 token 的部分在监督里被默默扔掉**。若你把 `max_tokens` 提到接近或超过 `cutoff_len`，却不在训练中同步放宽窗口，等于一边造长文本、一边只让模型看开头——这也是很多「明明数据很长、PPL 却不降」的隐蔽原因之一。

关键代码：

```python
model = lazyllm.TrainableModule(BASE_MODEL_PATH, target_path=target_path)
model.mode('finetune')\
    .trainset(TRAIN_JSON_PATH)\
    .finetune_method((finetune.llamafactory, {
        'stage': 'pt',
        'finetuning_type': 'full',
        'learning_rate': 3e-5,
        'cutoff_len': 512,
        'val_size': 0.05,
        'per_device_train_batch_size': 8,
        'gradient_accumulation_steps': 4,
        'num_train_epochs': 20,
        'lr_scheduler_type': 'cosine',
        'warmup_ratio': 0.1,
        'save_steps': 20,
        'save_total_limit': 5,
        'launcher': launchers.empty(ngpus=1),
    }))\
    .update()
```

参数简述：

- `cutoff_len=512`：单样本最大 token 长度；超过该长度会被截断，直接决定模型单次看到的上下文窗口。
- `per_device_train_batch_size=8`：每张 GPU 单步处理样本数；增大可提升吞吐，但会增加显存占用。
- `gradient_accumulation_steps=4`：梯度累积步数；等效总 batch 约为 `8 x 4`（单卡场景），用于在显存受限时稳定优化。
- `num_train_epochs=20`：完整遍历训练集的轮数；轮数过少易欠拟合，过多可能带来过拟合。
- `learning_rate=3e-5`：优化器初始学习率；值偏大可能训练不稳，偏小则收敛变慢。
- `warmup_ratio=0.1`：前 10% 训练步线性预热学习率，降低训练初期梯度震荡风险。

读完本节，建议你做一个「五秒钟自检」：**我的 `cutoff_len` 是否覆盖数据上常见的长度？batch 与 grad accumulation 的乘积是否大到让学习率显得偏小或偏大？** 这两个问题比纠结「epoch 要不要多加 5」更能决定是否训练得动、是否训得稳。

## 5. 通用评测方式

两实验都用“给定前缀，评 continuation”的统一方式，这是刻意设计：**比较两条数据流时，不能让评测接口再引入第三种差异**。在这个接口下，`prefix` 是「模型已知的上文」，continuation 是「要考它的下文」——实验 A 的 continuation 是真维基续写，实验 B 的 continuation 则是标准答案串。

- 计算 continuation 区间的 token 级交叉熵平均 loss
- 报告语料级 PPL
- 生成续写并计算 BLEU（2-gram F1 近似）

把 prefix 标签置为 `-100` 再算 loss，是在模仿人类考官：**前缀可以随便长，我只根据你续出来的部分打分**。若不这样做，模型在 prefix 上极容易预测的部分会「刷低」loss，评测就不再对续写质量敏感。

公式定义：

- PPL 与 Loss 关系：
$$
\mathrm{PPL} = \exp(\bar{L})
$$
**公式含义**：把 continuation 上的平均 token 交叉熵 $\bar{L}$ 取指数，得到「平均意义下模型还有多少种近似均等的下一词选择」的直觉度量；$\bar{L}$ 越低，PPL 越低。

**变量说明**：

- $\bar{L}$：全体评测样本上，continuation 区间 loss 的样本平均；每个样本内部先按 token 平均，再对样本做算术平均（实现以脚本为准）。
- $\mathrm{PPL}$：由 $\bar{L}$ 指数变换得到的困惑度标量，用于汇报与横向对比。

- BLEU（本实验近似）：
$$
F_1 = \frac{2PR}{P+R}
$$
**公式含义**：把 2-gram 视角下的「精确率」与「召回率」做调和平均，得到一个介于 $[0,1]$ 的标量，数值越大表示生成与参考在局部共现上越接近。

**变量说明**：

- $P$：2-gram precision，生成文本的二元组有多少比例落在参考二元组集合中。
- $R$：2-gram recall，参考二元组有多少比例被生成文本覆盖到。
- $F_1$：二者的调和平均，用于本课快速对比生成重合度。

关键评测函数（节选）：

1) `compute_ppl()`：只在 continuation 区间计算 loss/PPL

```python
def compute_ppl(model, tokenizer, samples):
    ppl_list, loss_list = [], []
    for item in samples:
        prefix, continuation = item['prefix'], item['continuation']
        full_text = prefix + continuation
        enc = tokenizer(full_text, return_tensors='pt', truncation=True, max_length=2048)
        prefix_enc = tokenizer(prefix, return_tensors='pt')
        seq_len = enc.input_ids.size(1)
        prefix_len = min(prefix_enc.input_ids.size(1), seq_len - 1)
        labels = enc.input_ids.clone()
        labels[:, :prefix_len] = -100
        with torch.no_grad():
            loss = model(input_ids=enc.input_ids, labels=labels).loss.item()
        loss_list.append(loss)
        ppl_list.append(torch.exp(torch.tensor(loss)).item())
    avg_loss = sum(loss_list) / len(loss_list)
    avg_ppl = torch.exp(torch.tensor(avg_loss)).item()
    return avg_ppl, avg_loss, ppl_list, loss_list
```

通过把 prefix 位置标签置为 `-100`，该函数只统计 continuation 的预测误差，避免前缀部分干扰评测。

2) `_bleu_simple()`：计算 2-gram F1 近似 BLEU

```python
def _bleu_simple(ref, pred):
    def _ngrams(s, n):
        s = ''.join(s.split())
        return [s[i:i + n] for i in range(len(s) - n + 1)] if len(s) >= n else []
    bigram_r = set(_ngrams(ref, 2))
    bigram_p = _ngrams(pred, 2)
    hit = sum(1 for b in bigram_p if b in bigram_r)
    prec = hit / len(bigram_p) if bigram_p else 0.0
    rec = hit / len(bigram_r) if bigram_r else 0.0
    return 2 * prec * rec / (prec + rec) if prec + rec else 0.0
```

该实现轻量、可复现，适合快速比较不同数据流训练后的相对生成质量。

3) `run_generation()`：批量生成并汇总 BLEU

```python
def run_generation(model, tokenizer, samples):
    results = []
    for start in range(0, len(samples), GEN_BATCH_SIZE):
        batch_items = samples[start:start + GEN_BATCH_SIZE]
        prefixes = [item['prefix'] for item in batch_items]
        enc = tokenizer(prefixes, return_tensors='pt', padding=True, truncation=True).to(DEVICE)
        with torch.no_grad():
            gen = model.generate(**enc, generation_config=gen_config)
        for i, item in enumerate(batch_items):
            pred = tokenizer.decode(gen[i], skip_special_tokens=True)
            ref = item['continuation']
            results.append({'bleu': _bleu_simple(ref, pred)})
    avg_bleu = sum(r['bleu'] for r in results) / len(results)
    return avg_bleu, results
```

该函数负责把“生成 + 指标计算”串起来，返回样本级结果与整体平均 BLEU，便于后续写入结果文件。

评测主干调用（节选）：

```python
avg_ppl, avg_loss, ppl_list, loss_list = compute_ppl(model, tokenizer, samples)
avg_bleu, gen_results = run_generation(model, tokenizer, samples)
```

该评测框架便于横向比较“不同数据流构造的训练集”对同一基座模型的影响。

最后补一句「读指标的良心话」：**PPL/Loss 变漂亮只说明模型更拟合你给的 continuation 分布**；**BLEU 变漂亮只说明生成更像参考句子**。若线上任务是开放作答，BLEU 仅供参考；若你是「固定标答」场景，BLEU 反而可能更有用。本课同时给三者，是让你习惯**多指标联合叙事**，而不是迷信单一数字。

## 6. 一条龙运行方式

两个脚本都支持相同入口模式：

- `--mode prepare`：只做数据准备
- `--mode train`：数据准备 + 训练
- `--mode eval`：只评测
- `--mode full`：准备 + 训练 + 评测

示例命令：

```bash
python run_wikitext.py --mode full
python run_phi4_wikitext.py --mode full
```

实践建议：

1. 先跑纯文本 pipeline，建立稳定 baseline。
2. 再跑 Phi-4 合成 pipeline，比较 PPL/Loss/BLEU 变化。
3. 若 BLEU 不升反降，可后续加一轮 SFT 或改为“仅 answer 区间”建模来做对齐优化。

环境与心态上的提示：**`prepare` 可能涉及 HuggingFace 数据集下载与本地缓存**，请先确认网络与磁盘；**含 LLM 的合成 pipeline 耗时会明显长于纯清洗**，适合用 `nohup` 或作业调度器挂后台。若中途失败，优先在 `data/` 里找「最后成功写盘的文件」定位卡在哪一步，再决定是重跑还是续跑。

第一次跑通后，建议你做的不是立刻改超参，而是**固定随机种子与数据文件**，只改一个变量（例如 `NUM_QA` 或 `max_tokens`），培养「单因素实验」的习惯——否则第 7 节的表格很难解释。

## 7. 实验1 vs 实验2 评测结果

**实验 1（纯文本 Pipeline）：**

| 模型 | PPL | Loss | BLEU |
|---|---:|---:|---:|
| 基座模型 | 21.2544 | 3.0566 | 0.9663 |
| 预训练模型 | 2.3141 | 0.8390 | 0.8023 |

**实验 2（Phi-4 Pipeline）：**

| 模型 | PPL | Loss | BLEU |
|---|---:|---:|---:|
| 基座模型 | 13.8500 | 2.6280 | 0.6890 |
| 预训练模型 | 3.1200 | 1.1390 | 0.6560 |

**实验 1 VS 2 对比（仅预训练模型）：**

| 实验 | PPL | Loss | BLEU |
|---|---:|---:|---:|
| 实验1（纯文本 Pipeline） | 2.3141 | 0.8390 | 0.8023 |
| 实验2（Phi-4 Pipeline） | 3.1200 | 1.1390 | 0.6560 |

实验2 相对实验1 的变化率：

$$
\Delta_{\text{metric}} = \frac{\text{metric}_{E2} - \text{metric}_{E1}}{\text{metric}_{E1}} \times 100\%
$$

**公式含义**：度量「实验 2（Phi-4 数据流）」相对「实验 1（纯文本数据流）」在同一指标上**百分比变化**；正值表示实验 2 更高，负值表示实验 2 更低（对 PPL / Loss 来说通常越小越好，因此正值反而代表实验 2 变差）。

**变量说明**：

- $\text{metric}_{E1}$：实验 1 PT 模型在该指标上的取值。
- $\text{metric}_{E2}$：实验 2 PT 模型在同一指标上的取值。
- $\Delta_{\text{metric}}$：相对变化率（百分数），用于快速比较两条数据流的差距量级。

按该公式计算得到：PPL 约 $+34.83\%$，Loss 约 $+35.76\%$，BLEU 约 $-18.23\%$。

**结果解读：**

- **实验1内部变化**：PPL 与 Loss 大幅下降，说明纯文本清洗分块后的继续预训练显著增强了连续文本续写建模能力；BLEU 下降说明“语言模型更拟合分布”与“与参考文本 n-gram 重叠”并不总是同步。
- **实验2内部变化**：PPL 与 Loss 同样明显下降，说明模型对 Q&A 分布的条件生成更稳定；BLEU 小幅下降，符合“仅做 PT、未做答案格式对齐”时的常见现象。
- **实验间结论**：在当前评测口径下，实验1的预训练模型在 PPL/Loss/BLEU 三项上都优于实验2，说明“纯文本 continuation 任务”与实验1的数据流更一致。
- **后续优化建议**：若目标是提升实验2的 BLEU，可考虑加入 SFT（Q/A 对齐）或将训练目标改为“answer 区间损失”，减少 Question 前缀对优化目标的干扰。

---

本课的表格不是在宣布「实验 A 压倒实验 B」，而是在演示**同量级的训练预算下，数据流如何重塑指标**。实验 1 更占便宜的地方在于——评测 continuation 与训练 `text` 同属「维基正文续写」这一族分布；实验 2 则把大量 token 预算花在 Question 模板与问答节奏上，continuation 更短、更离散，PPL 绝对值与 BLEU 都与实验 1 不可直接同比「谁绝对更好」，而应理解成**优化目标是否一致**。你带着这份表回到业务场景时，真正该问的是：**线上一致评测 continuation 到底是什么？** 若线上是聊天式多轮问答，本课评测只是保守近似，你还需要补意图识别、槽位、拒答、工具调用等维度，那已属于系统能力，而不是单点 PT 能画完的圆。

如果你读到这里已经跑通两个 `full`，恭喜你：你完成的其实是一次小型 **data-centric** 实验——这比记住一堆 LazyLLM API 名字更有迁移价值。下一步你可以试着只改 pipeline 参数或换一份语料，复用同一训练与评测脚本，你会很快发现：**指标曲线的形状，往往早在你点下 `prepare` 的那一刻就写好了伏笔。**
